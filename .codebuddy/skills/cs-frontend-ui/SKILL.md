# Frontend UI Engineering

## Overview

Build production-quality user interfaces that are accessible, performant, and visually polished. The goal is UI that looks like it was built by a design-aware engineer — not like it was generated by an AI. This means real design system adherence, proper accessibility, thoughtful interaction patterns, and no generic "AI aesthetic."

**Domain Owner:** When this skill is used to implement a frontend-owned slice (primary owner: `frontend` in the task plan), **FAN-OUT to `cs-frontend-lead`** (via `Task`). The lead owns the implementation; this skill provides the engineering standards. Contract-first: the UI consumes the API contract from `cs-backend-lead` / `cs-api-design` — never invent endpoint shapes.

## When to Use

- Building new UI components or pages
- Modifying existing user-facing interfaces
- Implementing responsive layouts
- Adding interactivity or state management
- Fixing visual or UX issues

## Component Architecture

### File Structure
Colocate everything related to a component:
```
src/components/TaskList/
  TaskList.tsx          # Component implementation
  TaskList.test.tsx     # Tests
  TaskList.module.css   # Scoped styles (or Tailwind)
  index.ts              # Public exports
```

### Component Design Rules
1. **Single responsibility:** One component = one conceptual piece of UI
2. **Composition over configuration:** Prefer composing small components over props-driven monoliths
3. **Presentational vs Container:** Separate display from data-fetching
4. **Controlled components:** Lift state to the right level

## Design System Adherence

- Use existing design tokens (colors, spacing, typography) — don't invent new ones
- Follow the project's component patterns
- Maintain visual consistency with existing UI

## Accessibility (WCAG 2.1 AA)

- Keyboard navigation for all interactive elements
- Semantic HTML (use `<button>` not `<div onClick>`)
- ARIA labels where semantics aren't enough
- Color contrast ≥ 4.5:1 for text
- Focus management (visible focus indicators, logical tab order)
- Screen reader support (alt text, aria-live regions)

## State Management

- Local state for component-specific data
- Lifted state for shared data between siblings
- Context for global-ish state (theme, auth, locale)
- External store for complex global state

## Performance

- Avoid unnecessary re-renders
- Memoize expensive computations
- Virtualize long lists
- Lazy load below-the-fold content
- Optimize images (responsive sizes, lazy loading, modern formats)

## Visual Quality (Anti-AI-Slop)

Production UI must not look like "AI generated." Avoid these telltale patterns:

| Avoid (AI slop) | Use instead |
|---|---|
| Purple gradients as default "tech" aesthetic | Brand colors or deliberately chosen palette |
| Emoji as bullet icons | Semantic icons from a design system, or none |
| Rounded card + left colored border accent | Honest visual hierarchy through spacing/typography |
| SVG hand-drawn faces/illustrations | Real images or honest placeholders |
| Uniform "everything is equally polished" | One detail at 120% (hero section, empty state, loading skeleton), rest at 80% — taste is knowing where to invest |

**Source**: Adapted from huashu-design's anti-AI-slop principles.

## Common Anti-patterns

- State duplication instead of lifting
- Over-memoization (memo/callback wrapping everything "just in case")
- Over-eager useEffect dependencies causing redundant re-renders
- Generic "AI aesthetic" — placeholder designs without real personality

## Verification

- [ ] Component is accessible (keyboard, screen reader, contrast)
- [ ] Responsive across target breakpoints
- [ ] Follows design system conventions
- [ ] No performance regressions
- [ ] Tests cover component behavior
- [ ] Visual output matches design intent

## Orchestration

- **Frontend slice implementation** → FAN-OUT to `cs-frontend-lead`
- **Browser verification** → FAN-OUT to `cs-frontend-lead` via `cs-browser-test`
- **Backend contract consumed** → supplied by `cs-backend-lead` / `cs-api-design`; if missing, stop and request it
- **Architecture boundaries** → set by `cs-architect`; surface disagreements in the report, do not silently redesign
- **Tests** → follow `cs-tdd` for frontend logic; component tests cover behavior, not implementation details
