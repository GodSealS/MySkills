# 文档驱动开发使用方法

本文说明本仓库的文档驱动开发（Documentation-Driven Development，DDD）工作方式，以及 Skill、command 和各开发阶段的执行顺序。

## 1. 核心概念

### Skill 是什么

Skill 是一套可复用的工作规程，描述何时使用、执行步骤、协作边界和验证标准。例如 `cs-tdd` 规定 RED → GREEN → REFACTOR，`cs-code-review` 规定五轴审查。Skill 可以被 command 调用，也可以直接调用。

### Command 是什么

Command 是面向使用者的入口（例如 `/cs-spec`、`/cs-build`）。它负责接收参数、选择模式、编排一个或多个 Skill，并设置人工确认点。Command 通常较薄，具体方法由 Skill 定义。

两者的关系可以概括为：

```text
用户 → command（入口/编排）→ skill（执行规程）→ 产物、代码、测试和验证结果
```

本仓库的源文件位于 `.codebuddy/`；根目录下的 `skills/`、`commands/` 是已生成的中性副本。修改源文件后，应运行适配器构建脚本同步各平台目录。

## 2. 以 SysDocs 为核心

文档驱动开发的中心不是某一个 command，而是项目根目录下的 `SysDocs/` 文档库。代码变更必须从文档读取上下文，完成后再把结构和边界写回文档，形成可追踪的闭环：

```text
SysDocs（当前系统地图）
    ↓ 读取边界、术语、模块职责和符号引用
需求/设计/任务（本次变更的意图）
    ↓ 指导实现与验证
源代码、测试、配置
    ↓ 反映实际结构和漂移
cs-sysdocs-update → 更新 SysDocs，供下一次变更继续使用
```

### 2.1 SysDocs 中各类文档的职责

| 文档 | 职责 | 开发时的使用方式 |
|---|---|---|
| `SysDocs/SYSTEM_ROOT.md` | 唯一入口；维护术语、系统范围、模块 manifest、依赖方向和全局约束。 | 每次任务先读它，确认项目边界和应进入哪个模块。 |
| `SysDocs/modules/<module-id>.md` | 描述一个模块的职责、流程、接口、数据和源码符号。 | 计划和实现前读取相关模块；模块边界变化时必须更新。 |
| `SysDocs/modules/<module-id>/<page-id>.md` | 可选的模块拆分页。 | 仅在 manifest 登记后使用，不能创建未登记的孤儿页面。 |
| `SysDocs/VibeCoding/*.md` | 碎片需求的临时草案，等待架构审查和合并。 | 只记录想法，不直接替代规格或写源代码。 |
| `SysDocs/.meta/` | 运行报告、迁移、恢复和 validator 结果。 | 用于审计和故障恢复，不当作模块正文。 |

### 2.2 文档状态是开发门闩

先做三态盘点，再决定入口；不能仅凭 `SysDocs/` 目录是否存在判断：

| 状态 | 含义 | 入口 |
|---|---|---|
| `UNINITIALIZED` | 没有有效的 `SYSTEM_ROOT.md`/模块文档，或只有空目录、`VibeCoding/`。 | `cs-sysdocs-init`，生成总文档和模块文档。 |
| `PARTIAL-INITIALIZED` | 文档结构不完整、manifest 不一致或 init 中断。 | `cs-sysdocs-update --mode repair`，先修复再开发。 |
| `INITIALIZED` | 总文档、manifest、模块文档完整且一致。 | `cs-sysdocs-update --mode incremental`，按代码漂移增量刷新。 |

文档状态 `draft`、`active`、`stale`、`archived` 也有实际含义：只有通过结构、引用、符号和 validator 检查后才能标为 `active`；源码漂移或修复未完成时应为 `stale`，不能假装文档仍是最新。

初始化有两个合法入口：已有源码的项目按代码证据执行 `cs-sysdocs-init`；只有需求/规格、尚无源码的项目先用 `/cs-spec` 形成规格，再执行 `cs-sysdocs-init --type spec` 生成文档骨架。既没有源码也没有规格时，不能猜测模块，必须先补充项目输入。

### 2.3 每次变更的文档责任

1. 开始前读取 `SYSTEM_ROOT.md` 和受影响模块文档，确认术语、边界、依赖方向和已有约束。
2. 需求若是碎片想法，显式使用 `cs-vibe-coding` 记录草案并等待架构审查；未初始化项目先执行 `cs-sysdocs-init`。
3. 计划必须引用受影响模块和文档中的边界，不从源码目录凭感觉重新猜边界。
4. 实现若改变模块职责、接口、数据流、符号或页面 manifest，代码与 SysDocs 必须一起更新。
5. 合并或发布前执行 `cs-sysdocs-update`，确认漂移、孤儿文档、符号引用和 Vibe 合并结果，并保留 `.meta/reports/` 报告。

### 2.4 一个任务的文档闭环

| 步骤 | 读取 | 执行 | 必须写回/产生 |
|---|---|---|---|
| 1. 定位 | `SYSTEM_ROOT.md`、模块 manifest | 判断项目状态和受影响模块 | 状态选择和范围记录 |
| 2. 澄清 | 术语表、模块职责、已有约束 | `cs-interview-me` / `cs-idea-refine`（需要时） | 明确目标、边界和验收条件 |
| 3. 设计 | 相关模块文档、依赖方向 | `cs-spec-driven`、`cs-architect`、`cs-docs-adrs` | `SPEC.md`、ADR、设计取舍 |
| 4. 压力测试 | 规格和风险假设 | `cs-grill-me` | `SPEC.md` 的 `## Grill Review` 决策 |
| 5. 拆解 | 模块边界和符号引用 | `cs-planning` | `tasks/plan.md`、`tasks/todo.md` |
| 6. 实现 | 任务、模块文档和代码模式 | `cs-incremental` + `cs-tdd` 及领域 Skill | 代码、测试、构建和原子提交 |
| 7. 同步 | 变更后的源码、manifest 和 Vibe 草案 | `cs-sysdocs-update` | 更新模块文档、状态、引用和 `.meta/reports/` |
| 8. 交付 | 审查报告、测试报告、文档 validator 结果 | `cs-code-review`、`cs-shipping` | 审查结论、发布记录和回滚方案 |

## 3. Skill 清单与解决的问题

### Define：定义问题

| Skill | 解决的问题 |
|---|---|
| `cs-interview-me` | 需求含糊时，通过一次一个问题提取真实目标、用户和约束。 |
| `cs-idea-refine` | 将粗略想法发散、比较并收敛为可执行概念。 |
| `cs-grill-me` | 对方案、规格或架构做对抗式压力测试，暴露假设、风险和遗漏。 |
| `cs-spec-driven` | 在编码前形成规格，固定目标、命令、结构、风格、测试和边界。 |

### Plan：计划

| Skill | 解决的问题 |
|---|---|
| `cs-planning` | 将规格拆成有依赖顺序、验收标准、验证步骤和主负责人的小任务。 |

### Build：构建

| Skill | 解决的问题 |
|---|---|
| `cs-incremental` | 用可回滚的垂直切片交付多文件或较大变更，保持每步可编译、可验证。 |
| `cs-minimal` | 新增实现、依赖或抽象前，优先复用现有代码、标准库、平台能力和已安装依赖。 |
| `cs-tdd` | 以测试驱动行为变更：RED（失败测试）→ GREEN（最小实现）→ REFACTOR。 |
| `cs-context-eng` | 在新会话、任务切换或上下文不足时整理项目规则和必要背景。 |
| `cs-source-driven` | 从官方文档提取依据，降低框架和库的过时用法风险。 |
| `cs-doubt-driven` | 对高风险或不熟悉的非平凡决策进行独立的 CLAIM → EXTRACT → DOUBT → RECONCILE 审查。 |
| `cs-frontend-ui` | 构建符合项目设计和可用性约定的生产级界面。 |
| `cs-api-design` | 设计稳定的 API、模块边界和前后端接口契约。 |
| `cs-team-build` | 让架构师拆解、领域负责人实现、审查员复核、测试工程师验收，形成可恢复的团队交付轨迹。 |

### Verify：验证与排障

| Skill | 解决的问题 |
|---|---|
| `cs-browser-test` | 在真实浏览器中检查 DOM、交互、控制台、网络、性能和可访问性。 |
| `cs-debugging` | 通过复现 → 定位 → 缩小范围 → 修复根因 → 回归保护，处理失败或异常行为。 |

### Review：审查与质量

| Skill | 解决的问题 |
|---|---|
| `cs-code-review` | 从正确性、可读性、架构、安全、性能五个维度审查变更。 |
| `cs-simplify` | 在不改变行为的前提下降低复杂度、重复和不必要的抽象。 |
| `cs-security` | 对输入、认证、敏感数据和外部集成建立威胁模型并落实 OWASP 防护。 |
| `cs-perf-opt` | 先测量基线，再定位瓶颈、优化并复测，避免无证据的微优化。 |

### Ship：提交与发布

| Skill | 解决的问题 |
|---|---|
| `cs-git-workflow` | 组织分支、原子提交、提交前检查和可回滚的保存点。 |
| `cs-cicd` | 配置 CI/CD、自动化测试和质量门禁。 |
| `cs-deprecation` | 安全下线旧系统/API，并规划迁移、兼容期和退出条件。 |
| `cs-docs-adrs` | 记录架构决策、设计理由、权衡和面向未来维护者的上下文。 |
| `cs-observability` | 增加结构化日志、指标、追踪和告警，使生产行为可诊断。 |
| `cs-shipping` | 执行发布前检查，确认监控、分阶段发布和回滚方案。 |

### SysDocs：系统文档

| Skill | 解决的问题 |
|---|---|
| `cs-sysdocs-init` | 对未初始化项目一次性生成 `SysDocs/SYSTEM_ROOT.md` 和模块文档。 |
| `cs-sysdocs-update` | 对部分初始化或已初始化项目执行 repair、incremental 或边界重建，并处理漂移和 Vibe 文档合并。 |
| `cs-vibe-coding` | 将碎片需求记录为经架构审查的 `SysDocs/VibeCoding/` 草案；不直接写源代码。 |

### Meta：路由与知识工具

| Skill | 解决的问题 |
|---|---|
| `cs-using` | 根据任务所处阶段发现并选择适用 Skill，是总路由规则。 |
| `cs-code-query` | 将代码查询、创建和更新路由到 CodeGraph、Understand-Anything 或 Graphify 知识库。 |
| `cs-agent-brief-review` | 审查给 AFK Agent 的任务说明是否具备持久性、行为目标、验收标准和范围边界。 |
| `cs-skill-review` | 从调用、信息层级、粒度、修剪、引导词和失败模式六个维度审查 Skill。 |
| `cs-huashu-design` | 用 HTML 制作高保真原型、交互演示、动画、幻灯片和设计变体。 |

## 4. Command 清单

当前 `commands/` 提供 9 个用户入口：

| Command | 主要调用的 Skill | 用途 |
|---|---|---|
| `/cs-spec` | `cs-spec-driven` | 创建 `SPEC.md`，并要求架构审查和 Grill Review 决策。 |
| `/cs-plan` | `cs-planning` | 读取已通过 Grill Review 的规格，生成 `tasks/plan.md` 和 `tasks/todo.md`。 |
| `/cs-build` | `cs-incremental` + `cs-tdd` | 实现下一个任务；每个任务测试、构建、提交并更新状态。 |
| `/cs-test` | `cs-tdd`（浏览器问题另加 `cs-browser-test`） | 执行 TDD；Bug 使用 Prove-It 回归测试流程。 |
| `/cs-review` | `cs-code-review` | 对当前变更执行五轴代码审查。 |
| `/cs-code-simplify` | `cs-simplify` | 在测试保护下简化近期变更，并再次验证。 |
| `/cs-ship` | `cs-shipping` | 并行执行代码、安全、测试专项检查，汇总 GO/NO-GO 和回滚计划。 |
| `/cs-team <设计文档>` | `cs-team-build` | 以架构师、领域负责人、审查员和测试工程师协作实现设计文档。 |
| `/cs-webperf` | `cs-perf-opt`（由 `cs-web-perf-auditor` 执行） | 对 Web 应用执行 Quick 或 Deep 性能审计。 |

没有独立 command 文件的 Skill（如 `cs-security`、`cs-debugging`、`cs-grill-me`、`cs-sysdocs-update`）可直接按 Skill 名称调用；部分平台会将其暴露为 `/cs-grill-me` 这类快捷入口。平台也可能提供额外的适配器命令。

## 5. 标准项目开发顺序

### 5.1 新功能或较大变更（SysDocs 主轴）

```text
cs-using
  ↓
① 盘点 SysDocs 状态
  ├─ UNINITIALIZED（有源码） → cs-sysdocs-init
  ├─ UNINITIALIZED（仅有规格） → /cs-spec → cs-sysdocs-init --type spec
  ├─ PARTIAL        → cs-sysdocs-update --mode repair
  └─ INITIALIZED    → cs-sysdocs-update --mode incremental（先刷新漂移）
          ↓
② 读取 SYSTEM_ROOT + 受影响模块文档
  ├─ 碎片需求 → cs-vibe-coding → cs-architect 审查 → 等待合并条件
  └─ 明确功能 → /cs-spec（若尚无规格）→ cs-spec-driven
                  ├─ cs-architect + cs-docs-adrs
                  └─ /cs-grill-me → 在 SPEC.md 写入 ## Grill Review 决策
          ↓
③ /cs-plan → cs-planning
  └─ tasks/plan.md + tasks/todo.md（任务引用模块边界和验收标准）
          ↓
④ /cs-build（重复执行每个任务）
  ├─ cs-incremental：选一个垂直切片
  ├─ cs-tdd：RED → GREEN → REFACTOR
  ├─ 按领域补充 cs-frontend-ui / cs-api-design / cs-security 等
  ├─ 浏览器功能补充 cs-browser-test
  ├─ 回归测试 + 构建 + 类型检查 + lint
  ├─ cs-sysdocs-update：同步本切片造成的模块/符号/manifest 漂移
  └─ cs-git-workflow：每个任务一个原子提交
          ↓
⑤ /cs-review → cs-code-review
  ├─ 必要时 cs-simplify
  ├─ 安全风险 → cs-security
  └─ 性能风险 → cs-perf-opt
          ↓
⑥ 再次 cs-sysdocs-update + validator
  └─ 文档通过检查并回到正确状态后，/cs-ship → cs-shipping
```

关键门禁：任何实现前都要有可用的 SysDocs 上下文；`/cs-plan` 要求规格包含已完成的 `## Grill Review`；`/cs-build auto` 还要求工作区基线干净，并在开始全量执行前取得一次明确批准。任何测试无法通过时转入 `cs-debugging`，高风险或不可逆操作转入 `cs-doubt-driven` 并请求确认。

### 5.2 单个 Bug 修复

```text
读取 SYSTEM_ROOT + 相关模块文档
        → 复现问题 → /cs-test（cs-tdd Prove-It：先写失败的复现测试）
        → 修复根因 → 测试通过 → 全量回归
        → 浏览器问题加 cs-browser-test
        → cs-sysdocs-update 同步受影响模块
        → /cs-review → cs-git-workflow 提交
```

如果无法稳定复现、定位或通过测试，不要猜测修复；使用 `cs-debugging` 的系统化流程。

### 5.3 设计文档驱动的团队交付

```text
/cs-team <设计文档>
  → Preflight（读取 SysDocs，确认文档和 Git 基线）
  → Architect 分解（调用 cs-planning，等待人工批准）
  → 每个任务：领域负责人实现 → cs-code-reviewer 审查 → 修复/提交（最多 3 轮）
  → 每轮后同步受影响 SysDocs 模块
  → cs-test-engineer 全量测试
  → cs-architect 汇总最终报告
  → cs-sysdocs-update + validator
  → cs-shipping（需要发布时）
```

### 5.4 SysDocs 状态与维护命令

先判断项目状态：

```text
UNINITIALIZED  → cs-sysdocs-init
PARTIAL        → cs-sysdocs-update --mode repair
INITIALIZED    → cs-sysdocs-update --mode incremental
边界变化       → cs-sysdocs-update --mode rebuild-boundaries
```

碎片需求必须显式调用 `cs-vibe-coding`，且项目至少为 PARTIAL-INITIALIZED；它只生成草案并经架构审查，后续由 `cs-sysdocs-update` 按四项条件合并，不能直接替代规格或源代码实现。`cs-sysdocs-update` 遇到未初始化项目时必须停止并要求先执行 init，不能隐式回调 init。

## 6. 使用原则与检查点

1. 先写清楚“完成”的定义，再开始编码；规格、计划和代码一起维护。
2. Skill 按需叠加，不要求把全部 34 个 Skill 串行执行；由风险、领域和交付阶段决定。
3. 每个实现切片都必须有测试、构建和提交证据；不要以“看起来没问题”代替验证。
4. 安全、性能、浏览器和发布检查是条件性分支，但一旦触发就必须执行。
5. 文档解释“为什么”，代码表达“怎么做”；架构取舍写 ADR，系统结构写 SysDocs，用户可见变化更新 README/CHANGELOG。
6. 修改 `.codebuddy/` 后运行 `scripts/build-adapters.ps1`（Windows）或 `scripts/build-adapters.sh`（POSIX），确保各平台适配器同步。

## 7. 常用入口示例

```text
/cs-spec 新的订单导出功能
/cs-grill-me SPEC.md
/cs-plan
/cs-build                 # 只做下一个待办任务
/cs-build auto            # 规格和 Grill Review 完整后，经一次批准连续执行
/cs-review
/cs-ship
```

以上顺序是默认路径；小型单文件改动可以直接使用 `cs-incremental` + `cs-tdd`，紧急故障优先使用 `cs-debugging`，不必强行创建完整规格。
